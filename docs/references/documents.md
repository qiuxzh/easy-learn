# 文档使用说明

## 文档结构

docs/pitfalls 是项目中遇到的问题和解决方法的文档，遇到问题可先查看里面。

项目需求文档在 docs/require

# 文档更新说明

## 更新时机

- 如果过程中需求有变动，或者实际开发和需求文档不符，需要同步需求文档。

## 内容更新要求

- 文档的初衷是**指导开发**，不是用代码来解释文档：写代码之前看文档能少走弯路，而不是让文档把代码复述一遍
- 代码里一眼能看出来的内容不写进文档，例如一个类型有哪些字段、一个函数有哪些参数——这些直接看代码更轻松
- 不要把类型定义、字段清单做成表格来复述；除非它本身就是对外契约（配置文件格式、IPC 通道列表这类）
- 只写代码里看不出来的东西：为什么这样设计、必须遵守的约束、容易踩的坑
- 更新需求文档的要求:能不新增大标题尽量不需要新增大标题，防止层级过深
- 大标题禁止写序号，例如“一、需求分析”，防止增删标题时大面积标题改动
- 业务需求强相关，而不是实现强相关，防止技术重构时带来的文档同步负担
- 禁止写需要频繁同步的低层信息，例如代码的行号，否则后续改代码时还需同步文档
- 文档如果需要描述功能，只能写其对外保留的功能，不应该提供任何内部细节实现
