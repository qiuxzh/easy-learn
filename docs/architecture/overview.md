# 主进程架构

主进程按依赖方向分层，`bootstrap` 是唯一的装配根；除此之外，任何一层都不认识“整体应用”。

## 依赖方向

```
main/index.ts          启动流程：路径 → bootstrap → 注册 IPC → 开窗口 → 退出释放
  └── bootstrap.ts     装配根：创建 kernel、仓储与模块，按创建反序释放
        ├── ipc/       适配层：IPC 请求 → 用例调用；异常 → 结果
        ├── 模块/服务  业务：只依赖契约与端口，不依赖 electron 与数据库
        ├── contracts/ 实体、仓储契约与窄端口
        └── infra/     实现：连接、表结构、仓储与外部适配器
```

- `bootstrap` 可以认识所有模块；模块之间只能通过对方的公开 API 交互。
- 模块不接收数据库句柄，也不自行创建仓储；仓储由装配根统一创建后注入。
- 服务不 import `infra` 的具体实现；需要事务时注入事务端口，测试用同步执行替代。
- `contracts/` 只放类型与契约，不放实现；`infra/` 依赖 `contracts/`，反向不允许。

## 装配与生命周期

- 启动时在 `bootstrap` 内创建 kernel（数据库、配置、事件、路径）、全部仓储与各模块，再把模块公开的服务交给 `ipc`。
- 释放时按创建的反序进行：先停后台任务与会话，再退订配置，最后关闭数据库。
- 模块内部可以组装子服务与后台任务，但对外只暴露必要的服务；子服务不进入装配根的视野。
- 不设全局单例与 service locator；需要什么由构造参数显式传入。

## 事务

- 单聚合的多步写由仓储自己包事务，调用方不需要知道事务边界。
- 跨聚合或带文件系统的流程不做长事务，做可重入：先做幂等检查，失败留下阶段状态，下次继续。
- 需要多个聚合同时成功时，由用例服务注入事务端口开事务。
- 事务回调必须同步；嵌套事务加入外层，只有最外层决定提交或回滚。

## 约束

- 纯计算保持普通函数，不包成类。
- 同一规则只落在一个地方：过滤/排序/分页在 SQL，业务口径在校验层，序列化在 infra。
- 异步后台任务的启停必须可被装配根统一管理；不能只提供“开始”而没有退出路径。

## 已知缺口

- 分层仍靠约定，没有 lint 规则机械约束跨层 import。
- 表结构仍是 drizzle 声明与手写 DDL 两份，没有版本化迁移。
- 工具层与部分仓储行为缺少自动化测试。
