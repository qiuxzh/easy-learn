# 格式化电子书 .lb

## 痛点

扫描版 PDF 的每一页本质是一张图片：没有文本层，无法检索，无法做关键词 / 相似度 / 语义检索，也无法让 AI 直接引用书中原文。文本版 PDF 虽有文本层，但公式、图表、跨栏阅读顺序仍不可靠。

现有书籍能力（foliate + CFI + chunk + BM25）只覆盖"有干净文本结构"的 EPUB，覆盖不到上述场景。

`.lb` 的目的：把难以检索的载体离线转换成结构化、可定位、可被 AI 直接读的载体，同时保留原文件以便回退与对照。

## 目标与非目标

目标：

- 可检索：内容以文本形式落地，能被 BM25 / 向量检索命中；
- 可定位：每段内容能映射回原文件的物理位置，支持跳转与高亮；
- 可被 AI 读：AI 不必解析 PDF，直接读取结构化内容。

非目标：

- 图表描述、AI 解读等**生成**内容不属于书籍内容，归"外挂能力桥接器"，以注释形式存在，不与原文混在一起。否则检索会把模型编的话当作原文返回。

## 分层流程

输入适配层（确定性解析 + OCR）

- 嗅探载体类型：PDF 是扫描版还是文本版、EPUB 是否加密。
- 抽取原子信息：字符流、图像二进制流、页码边界、字体特征（粗体 / 斜体）、文本与图像在页内的物理坐标。
- 对没有文本层的内容调用 OCR / 多模态模型，产出文字与公式候选。
- 此层只提取，不做语义判断。

语义抽取与结构化引擎（大模型）

- 把原子信息交给大模型整合，判断内容类型、划分章节层级，产出带标签的结构对象：Text / Image / Math / Table / Section。
- 建议只输出"骨架与标签"，正文以输入适配层的原文为准。若让模型重写正文，会引入幻觉且成本极高（每页都要输出全文）。

容器封装器（.lb）

- 把结构化结果、原文件副本、页面位图打包压缩，并定义内部格式规范。
- 是结构与渲染之间唯一的契约。

本地渲染与交互引擎

- 渲染 .lb 内容，响应折叠、点击选项、划词等交互。
- 以重排为主，不还原原页版面。

外挂能力桥接器

- 需要外部算力（用户自备 API Key）的入口：AI 解释、AI 出题、图表描述等。

## 为什么分两遍

- OCR 对公式块不可靠。公式必须走单独通道（专门模型，或保留裁剪图兜底），不能指望整页识别。
- 整页图像无法给出页内子图像的坐标。页内图片的位置必须从文件自身的结构信息（PDF 页资源 / XObject、文本层）取，视觉模型给不了可靠坐标。

推论：

- 第一遍的主体是**文件解析**，不是"让多模态模型看图"；坐标的可信度来自文件结构。
- 因此两遍的分工是「可信原文与坐标」+「图像内容识别」对「语义判断」，不是两个等价的模型调用。
- 边界情况：源头若为纯位图（无 PDF 结构），坐标只能靠版面分析模型估计，可信度下降一档，需要在设计里承认。

## 锚点

锚点要同时服务三件事：跳转定位、用户数据挂载（高亮 / 笔记 / 闪卡 / 答题记录）、检索结果对齐。因此它必须在"重新生成 .lb"之后保持不变，否则用户数据整体错位——而语义结构是大模型产生的，天然不确定：换模型、改提示词、调温度都会让切分点漂移，甚至同一次调用也不保证幂等。

候选一：语义标识（模型给出的 section id / 序号路径）

- 可读性好，但非确定。重跑一次结构化，全书高亮、笔记、闪卡、embedding 全部失效。

候选二：物理锚点（页码 + 归一化 bbox；EPUB 用 spine 下标 + CFI）

- 只由原文件结构决定，只要原文件不变，重跑多少次结果都一致。
- 代价：可读性差；换到另一版原文件无法迁移——但那本就等于换了一本书。

建议：物理锚点做 ID，语义结构做覆盖层。

- 内容块（Block）是唯一带 ID 的单位，ID 编码物理锚点。
- Section 不产生 ID，它只是"一串块 ID 的有序引用"。
- 重新结构化 = 重建 section 树，块与用户数据不动。
- 用户数据挂载在（块 ID，块内字符区间）上。
- 若块本身被重切（换了 OCR 粒度），用 bbox 的包含 / 重叠关系迁移旧标注，迁移不了的收进"孤立标注"待用户认领。

格式规范必须写死的部分：锚点的编码方式与坐标系。建议用归一化坐标（0~1），避免绑定渲染 DPI。

连带影响：扫描页若要支持精确划词与高亮，需要词级甚至字符级 bbox，体积开销明显；若只支持整段选择，块级 bbox 足够。

## 索引与 embedding 的归属

建议：检索分块（chunk）进格式，向量不进格式。

- embedding 与具体模型、维度强绑定，写进格式等于"换模型即全部失效 + 全书重算"，且体积可观（数千 chunk × 上千维）。
- BM25 倒排索引带参数与停用词，同样属于可重建的派生物。
- 索引的消费方是本应用，放在应用侧（SQLite，与现有 EPUB chunk 流程一致）即可。

格式内保留 chunk（纯文本 + 锚点）有价值：它决定了 AI 与检索如何切分这本书，属于内容结构的一部分，不是可随意更换的实现细节。

## .lb 内部结构建议

```
meta.json       格式版本、生成器、各阶段所用模型与版本、生成时间
original/       原文件副本（不可变，用于回退与对照）
pages/          页面位图（不可变，派生自原文件）
blocks.jsonl    内容块，每行一块，带物理锚点、类型、溯源（不可变，派生）
structure.json  语义结构：section 树 + 块引用（不可变，可重跑重建）
user/           用户数据：笔记、高亮、闪卡挂载、答题记录（可变）
```

设计原则：

- 不可变部分（original / pages / blocks / structure）全部可由原文件重新生成；可变部分（user）只依赖块 ID，不受重跑影响。
- 每块带溯源信息（引擎 / 模型 / 版本 / 置信度），用于"只重跑低置信度的块"与排查错误。
- 类型标签用闭集，不用模型现造的词，否则无法按类型检索与过滤。
- Math 对象同时保留 LaTeX 与裁剪图片作为兜底。
- 未知类型 / 未知字段的读取策略要在规范里明确：忽略降级还是拒绝打开。

## 已定

- 分发：`.lb` 可能用于传播，但不追求成为开放格式，只保证本应用能解析。由此版本兼容是硬需求——接收方手里的包可能由旧版本生成，新版必须能读；已发布的字段与枚举一旦发出去就冻结，只能新增不能改语义。
- 中间产物落盘：OCR 结果与版面坐标留在包内，避免每次重跑都重新付出 OCR 成本。
- 渲染：以重排为主，不还原原页版面；不可重排的块（Math / Table / 图片）保留裁剪图原样呈现。

## 待决问题

- 体积：中间产物落盘与传播场景直接冲突。既然要重排，页面位图是否还要随包分发？它只为"对照原样"而存，却是体积的大头。
- 原文副本的版权：包内自带原书副本，传播即二次分发原书。接受个人范围内分享，还是改为不内嵌。
- 用户数据是否随包传播：`user/` 在包内，把自己带笔记的 `.lb` 发出去会连笔记一起发出去，需要"导出时剥离用户数据"的规定。
- 容器载体：既然只被本应用解析，不必追求 zip + jsonl 的自描述形式，可以直接用一个 SQLite 文件（元信息、块、结构、用户数据都是表，图片走 blob）。省掉整套解析与索引代码，且支持部分读取。
- 可变内容放容器内还是应用数据库内。放外部则 `.lb` 纯为可丢弃缓存。
- `.lb` 与现有 EPUB 链路是替换还是并存。并存等于两套内容模型、双份维护。
- "AI 友好"的第一优先：纯文本易解析 / 稳定锚点可引用 / token 效率高，三者互相拉扯。
- 习题对象是否一等公民（题干、选项、答案、解析）。若无，"点击选项"没有语义。
- 原文副本与 OCR 结果不一致时以谁为准。
- 最小可验证切片：建议先只做"扫描页 → 可检索 + 可定位"一条链，其余都是它的下游。
