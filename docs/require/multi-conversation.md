# 多会话管理业务说明

## 概述

每个对话 Tab 是一个独立的对话会话上下文。用户可以在不同对话 Tab 中同时进行多个独立的 AI 对话，会话之间互不干扰。本文档说明多会话管理在用户视角下的核心规则与交互行为。

## 一对一占用规则

**一个对话在同一时刻最多只能被一个对话 Tab 占用**。即：

- 用户在 Tab A 中打开了"如何学习英语"这个对话，并继续对话
- 用户在 Tab B 中点击历史列表里的"如何学习英语"，系统应当拒绝切换并提示"该会话正在被其他标签页占用"

这一规则带来的业务价值：

- 避免多个 Tab 看到同一对话的不同步状态（例如一个 Tab 发送消息，另一个 Tab 也在发送，会话上下文冲突）
- 避免多个 Tab 同时操作同一会话导致的 UI / 状态竞争
- 用户对"我在哪个 Tab 看哪个对话"有清晰的预期，不会出现"我以为我在 Tab A，其实切到了 Tab B"的混乱

## 新建会话

用户在对话 Tab 内可通过"新建会话"按钮（位于头部右侧的 + 图标）开启一个全新会话：

- 点击后立即清空当前 Tab 的消息列表，Tab 回到空白"开始新对话"占位状态
- 关闭侧边历史面板
- 当用户发送第一条消息时，系统在后端创建新会话并持久化

这一约束让用户可以随时在同一个 Tab 内"重新开始"，而不需要关闭 Tab 再开新的。

## 切换会话

用户在历史面板点击任意会话条目时：

- 检查该会话是否被其他 Tab 占用。被占用则弹窗警告并阻止切换
- 释放当前 Tab 之前占用的会话（清理资源占用）
- 加载目标会话的消息历史（如果尚未在本地缓存）
- 当前 Tab 切换到目标会话上下文

切换是即时的，用户无需等待加载——本地有缓存就直接显示，没有则后台加载完成后自动展示。

## 关闭 Tab 时的会话处理

当用户关闭对话 Tab 时：

- 当前 Tab 占用中的会话被释放，不再归属于任何 Tab
- 如果该会话当前**不在流式响应中**（AI 没有正在生成），会话数据从内存清理。用户后续从历史列表点回此会话时，会从后端重新加载消息
- 如果该会话**正在流式响应**（AI 仍在生成），会话数据保留在内存中，但不再归属于任何 Tab。AI 后端继续推送响应，响应数据继续累积。其他 Tab 此时可以从历史列表接管这个会话，从接管那一刻起就能看到累积的响应内容

这一约束的核心考虑是"不打断正在进行的 AI 生成"——用户可能因为临时切到别的 Tab 看资料而关闭当前对话 Tab，AI 仍在生成的内容不应该丢失。

## 历史面板

历史面板（点击头部时钟图标打开）展示所有会话列表，按创建时间分组：

- 今天
- 昨天
- 前天
- 一周内
- 一个月内
- 一个月以上

面板从左侧滑出展开，再次点击时钟图标收起。

**每次打开历史面板时会自动刷新一次会话列表**，确保用户新建的会话能立刻在历史中看到。这一约束是因为会话的创建发生在前端，但后端持久化是异步的，前端需要重新拉取才能确认新建成功。

## 单条会话的维护

每条会话支持重命名与删除：

- **重命名**：点击条目右侧的更多按钮（hover 出现），选择"重命名"，输入新名称后回车提交
- **删除**：点击更多按钮选择"删除"，会话立即从历史中移除，相关消息也会一并删除（前端和后端同步）

## 业务上的取舍说明

- 选择"占用而非共享"而非"多 Tab 可看同一会话"，是为了避免 UI 状态同步复杂性。对绝大多数用户而言，对话是按主题或任务划分的，多 Tab 看同一会话的实际需求极少
- 选择"关闭 Tab 不 abort 流"而非"关闭 Tab 立即停止 AI 生成"，是为了减少 AI 生成被打断的挫败感。用户关闭 Tab 通常只是临时操作，不应该让 AI 之前的工作白费
- 选择"orphan 流式会话保留在内存"而非"立即清理"，是为了支持其他 Tab 接管。后端流推送持续到来，如果立即清理会丢失后续内容
