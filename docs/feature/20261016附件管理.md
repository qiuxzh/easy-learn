## attachment表

大致结构

```sql
attachment(
  id        TEXT PRIMARY KEY,   -- uuid
  path      TEXT NOT NULL,      -- 磁盘相对路径（含扩展名）
  type      TEXT NOT NULL,      -- 'image'（枚举，预留扩展）
  mimeType  TEXT NOT NULL,
  size      INTEGER NOT NULL,
  createdAt INTEGER NOT NULL
)
```

纯字节账本：id → 文件位置 + 元数据。不记来源、不记归属、不做任何删除策略判断。

删除链路：

```
entry 被回收 → 遍历 content 提取 attachmentId → deleteMany
书删除 → 按 book.cover_attachment 读出封面附件 → deleteMany
```

不做启动对账：写文件成功但插行失败、删行成功但删文件失败，都会在附件目录留下没有对应行的残留文件，这些文件不会被回收。

删 entry 不会误删书籍文件，原因是：entry content 里的 attachmentId 只有两个来源——用户上传、read 工具拷贝，且这两个来源每次都新建附件。书籍文件登记附件后，其 id 只存在 book 表里，没有任何代码路径会把它写进消息，所以删 entry 时提取到的 id 集合里不会有它。

前提是保持"每次读取必拷贝、不复用已有附件 id"。若将来改为按 id 复用，read-attachment-image 返回的就会是书籍文件自己的 id，它随 toolResult 写进 entry，删 entry 时就会被删掉。

## read-image 工具要求

read-image 拆分为 read-attachment-image 和 read-image 。

- read-attachment-image 支持根据 attachment 读取图片（不再是路径）
- read-image 支持根据路径读取图片

读取图片成功后会拷贝读取的图片文件，并写入 attachment 表，并返回含有 attachmentId 的 ImageContent
