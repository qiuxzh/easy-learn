# agent 事件系统

agent 模块自己定义的事件只有一种：`AgentEvent`，声明在 `src/shared/types/chat.ts`。按类别分，它的成员只有四组：

| 类别 | 成员                                             |
| ---- | ------------------------------------------------ |
| 运行 | `agent_start`、`agent_end`                       |
| turn | `turn_start`、`turn_end`                         |
| 消息 | `message_start`、`message_update`、`message_end` |
| 工具 | `tool_execution_start`、`tool_execution_end`     |

发出者是内核主循环，`Agent` 转发给订阅者之前先拿事件更新自身状态。运行期间严格串行，顺序就是真实发生顺序，没有并发。

两处得离开这张表单独讲：

- `message_update` 的 `assistantMessageEvent` 字段装的是模型适配层的流式事件。它不是内核事件，而是内核从适配器的流里逐条翻出来的，见「适配器流 → 内核事件」。
- `AgentSession` 在转发内核事件之外，自己另加一个 `queue_update`，见「AgentSessionEvent」。

标记为「运行序列」的图里**全部是 `AgentEvent`**；`AssistantMessageEvent` 只活在 `StreamFn` 返回的那条流内部。图里行尾的 `← 适配器 …` 注的是这一行由哪个适配器成员翻出来。

## 适配器流 → 内核事件

这是全文唯一能看到 `AssistantMessageEvent` 的地方。假设助手这次先思考、再说话、再调一个工具：

```
适配器流（StreamFn 内部，AssistantMessageEvent）        内核据此发出（AgentEvent）
├─ start          { partial }                        → message_start  { assistant }
├─ thinking_start { contentIndex: 0 }                → message_update
├─ thinking_delta { 0, "先看看配置…" }                → message_update
├─ thinking_end   { 0, "先看看配置…" }                → message_update
├─ text_start     { contentIndex: 1 }                → message_update
├─ text_delta     { 1, "我看看 " }                    → message_update
├─ text_end       { 1, "我看看 config.json" }         → message_update
├─ toolcall_start { contentIndex: 2 }                → message_update
├─ toolcall_delta { 2, "{\"path\":" }                → message_update
├─ toolcall_end   { 2, toolCall }                    → message_update
└─ done           { message }                        → message_end    { assistant }
```

两边**一一对应、按到达顺序**：左列一条，右列一条。翻译规则只有三条：

| 适配器成员                                    | 内核发的事件                                                                                  |
| --------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `start`                                       | `message_start`，携带的 `partial` 是这条助手消息（`content` 为空，`stopReason` 为 `pending`） |
| 9 个块级成员（`text_start` … `toolcall_end`） | `message_update`，`message` 为当前 partial，`assistantMessageEvent` 就是左列那条原始事件      |
| `done` / `error`                              | `message_end`，携带定稿消息。用 `error` 收尾时消息的 `stopReason` 为 `error` / `aborted`      |

推论：`start` / `done` / `error` 永远不会出现在 `message_update.assistantMessageEvent` 里，它只可能是那 9 个块级成员。

### AssistantMessageEvent 的成员

它不是内核事件，而是某条 API 协议的流式线格式——适配器的职责就是把自己的协议投影成这一套。`for await` 一条 `StreamFn` 返回的流，拿到的就是这些。

| 成员                            | 载荷                                  | 含义                                                                                                           |
| ------------------------------- | ------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `start`                         | `partial`                             | 一次请求的开始。适配器在**发出请求之前**就发它，所以即使请求立刻失败，后续消息生命周期也是完整的               |
| `text_start` / `thinking_start` | `contentIndex`、`partial`             | 新建一个文本块 / 思考块。按"当前块类型是否变化"判断，所以一条消息里可以有多个同类块                            |
| `text_delta` / `thinking_delta` | `contentIndex`、`delta`、`partial`    | 该块的增量                                                                                                     |
| `text_end` / `thinking_end`     | `contentIndex`、`content`、`partial`  | 该块定稿，`content` 是整块内容                                                                                 |
| `toolcall_start`                | `contentIndex`、`partial`             | 新建工具调用块，通常出现在首帧带回 `id` 与 `name` 时                                                           |
| `toolcall_delta`                | `contentIndex`、`delta`、`partial`    | 工具入参 JSON 的片段，消费方自己拼接                                                                           |
| `toolcall_end`                  | `contentIndex`、`toolCall`、`partial` | 工具调用定稿，`arguments` 已解析成对象。适配器在**整个流读完之后**统一补发，必然排在所有 `toolcall_delta` 之后 |
| `done`                          | `reason`、`message`                   | 正常收尾                                                                                                       |
| `error`                         | `reason`、`error`                     | 失败或中止收尾                                                                                                 |

## 运行序列（以下全部是 AgentEvent）

### 一问一答

`prompt("你好")`：

```
├─ agent_start
├─ turn_start
├─ message_start   { user }              提示词进对话记录
├─ message_end     { user }
├─ message_start   { assistant }         ← 适配器 start
├─ message_update  × n                  ← 适配器 9 个块级成员，一条对一条
├─ message_end     { assistant }         ← 适配器 done / error
├─ turn_end        { message, toolResults: [] }
└─ agent_end       { messages: [user, assistant] }
```

### 助手要求工具

`prompt("看一下 config.json")`，助手先调工具再作答，于是 run 里有两个 turn：

```
├─ agent_start
├─ turn_start
├─ message_start/end  { user }
├─ message_start      { assistant，含 toolCall 块 }   ← 适配器 start
├─ message_update × n                               ← 适配器块级成员
├─ message_end        { assistant }                  ← 适配器 done
├─ tool_execution_start  { toolCallId, toolName, args }
├─ tool_execution_end    { toolCallId, toolName, result, isError }
├─ message_start/end  { toolResult }
├─ turn_end           { message: assistant, toolResults: [toolResult] }
│
├─ turn_start                                         第二个 turn，没有新的用户消息
├─ message_start      { assistant }                   直接就是助手在消化工具结果
├─ message_update × n
├─ message_end
├─ turn_end
└─ agent_end
```

要点：

- 工具结果自己走一遍消息生命周期，**但不构成新 turn**，它是本轮的收尾材料。
- 助手要求了工具，就一定还有下一个 turn——结果得交回模型，否则模型不知道工具跑出了什么。
- 一次要多个工具时，多个 `tool_execution_start` 会连在一起出现（默认并发），`tool_execution_end` 按各自跑完的顺序穿插；但随后的 `message_start/end` 和 `turn_end.toolResults` 一律按助手消息里的原始顺序。
- 只有"这一批工具结果全部要求提前终止"时才不开下一个 turn，直接 `agent_end`。

### 排队消息被注入

steering 与 follow-up 的**事件形状完全一样**，区别只在插入时机：steering 在本轮的工具结果之后注入（会改掉 run 原本的走向），follow-up 要等到"本来该 `agent_end` 了"才被取用。两者都落在 turn 边界上，因此都表现为"多出一个 turn，且这个 turn 先收到一条用户消息"：

```
运行中 steer("顺便看下 README")
├─ …                                       当前 turn 照常跑完
├─ turn_end
├─ turn_start                              注入点在 turn 边界
├─ message_start/end  { user }             被注入的排队消息
├─ message_start      { assistant }        模型消化它
├─ …
└─ agent_end
```

排队期间靠 `queue_update` 得知"已排队"，而不是靠上面这些事件——排队消息在被注入之前还不是消息。所以 `queue_update` 会零散地穿插在任意位置，序列图里不画它。

### 失败与中止

模型请求失败或用户中止时，**事件序列与正常运行完全一致**，只在末条助手消息上体现：

```
├─ agent_start
├─ turn_start
├─ message_start/end  { user }
├─ message_start      { assistant }
├─ （可能有 message_update）
├─ message_end        { assistant，stopReason 为 error 或 aborted，带 errorMessage }
├─ turn_end           { message, toolResults: [] }
└─ agent_end
```

没有单独的"成功/失败"事件，判断结局只能看末条助手消息。

更极端的情况是主循环自己抛异常（不是模型报错），由 `Agent.handleRunFailure` 兜底补发，缺 `agent_start`：

```
├─ message_start/end  { assistant，stopReason 为 error }
├─ turn_end
└─ agent_end          { messages: [这条失败消息] }
```

注意这里的 `agent_end.messages` 只有那条失败消息，不是本次运行的全部消息。

还有更靠前的失败：`Agent.prompt` 在进入主循环之前就可能抛错（例如已有 run 在跑），此时**一个事件都不会发出**。所以"运行中"这个标志不能靠 `agent_start` / `agent_end` 配对来维护，`AgentSession` 另有一套自己的标志。

## AgentEvent 的成员

| 事件                   | 载荷                                          | 含义                                                                                             |
| ---------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `agent_start`          | —                                             | 一次运行的第一个事件                                                                             |
| `turn_start`           | —                                             | 一个 turn 开始。首次 turn 由 `runAgentLoop` 发送，之后每轮由 `runLoop` 发送                      |
| `message_start`        | `message`                                     | 一条消息进入对话记录                                                                             |
| `message_update`       | `message`、`assistantMessageEvent`            | 助手消息流式期间的增量。**只有助手消息有**                                                       |
| `message_end`          | `message`                                     | 一条消息定稿                                                                                     |
| `tool_execution_start` | `toolCallId`、`toolName`、`args`              | 工具开始执行。参数校验、`beforeToolCall` 都在它之后                                              |
| `tool_execution_end`   | `toolCallId`、`toolName`、`result`、`isError` | 工具执行结束。`afterToolCall` 修正过的结果才在这里                                               |
| `turn_end`             | `message`、`toolResults`                      | 本 turn 的助手消息，以及这一批工具结果                                                           |
| `agent_end`            | `messages`                                    | 一次运行的最后一个事件，`messages` 是本次运行产生的全部消息。被 await 的订阅者仍算本次运行的结算 |

`Agent` 转发前先更新自身状态（`streamingMessage`、`pendingToolCalls`、`errorMessage`），再按注册顺序把事件交给订阅者，**逐个 `await`、严格串行**。所以"事件到达时状态已更新"对订阅者是保证。

## AgentSessionEvent

```
AgentSessionEvent = AgentEvent | QueueUpdateEvent
```

内核事件一律原样转发，不改名不裁剪、不额外插入。`queue_update` 是会话自己唯一产出的新增事件：

| 字段       | 含义                        |
| ---------- | --------------------------- |
| `steering` | 待注入的 steer 消息文本     |
| `followUp` | 待注入的 follow-up 消息文本 |

载荷是**全量快照**，在入队、清空、以及某条排队消息被真正消费掉时各广播一次。

转发时顺带三件副作用：

1. `message_end` 落库（只落 `user` / `assistant` / `toolResult`）；
2. `agent_start` / `agent_end` 维护会话自己的运行标志（`agent_end` 要等订阅者结算完才算空闲）；
3. 用户消息的 `message_start` 到达时，从待展示列表里摘掉对应文本并再广播一次 `queue_update`。

## 坑

- `message_start` / `message_end` 也为用户消息发出（提示词、注入的 steering / follow-up 都会走一遍），订阅者不能假定其 `role` 是 `assistant`。
- 一条消息是否落库只看 `message_end`；`message_update` 一律不落库。
- 判断运行结局只能看末条助手消息的 `stopReason` / `errorMessage`，没有单独的事件。`stopReason` 为 `error` / `aborted` 的助手消息**仍然会走完整的消息生命周期**，并且 `message_end` 也会落库。
- `agent_start` 与 `agent_end` **不保证成对**，甚至可能一个都不出现。
- 工具执行抛异常**不算运行失败**：异常被转成 `isError` 为 true 的结果，运行继续。
- `Agent.state.streamingMessage` 在用户消息的 `message_start` 时也会被赋成那条用户消息（`processEvents` 不区分 `role`），随后 `message_end` 立刻清掉。
- 工具并行执行时事件顺序与助手消息里的顺序**不一致**，只有持久化的工具结果消息保证按原始顺序。
