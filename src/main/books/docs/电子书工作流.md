# 电子书工作流(未定稿)

> 本文梳理「输入文件 → `.lb`」的整条链路，以及 `.lb` 自身的结构规范。
> 只讲主线判断与理由，不复述个案证据；架构分层见 `电子书流水线.md`。

---

## 1. 目标与痛点

- 电子书对 AI 阅读器不友好
- 全扫描版本的书，问 AI 一个问题**必须把图片传给 AI**
- 难以用 BM25、embedding 等技术做内容检索

统一解法：**把难以检索的形态，转成便于检索的形态**，落进一个自足的容器 `.lb`。

```
输入文件 ──[流水线]──► .lb ──[阅读器]──► HTML + 样式
```

阅读器不解析原始格式，只消费 `.lb` 的骨架并附样式。所以整条工作流的核心，是**把各种输入格式归一到同一套骨架**。

> 本文的当前范围是**把书转成 `.lb`**。痛点里"把图片传给 AI"这一条要靠引用定位能力解决，本版不做，记在第 11 节。

---

## 2. 核心判断：定义产物，而不是定义动作

朴素的三步会把 OCR 固定在中间：

|        | 朴素定义                    |
| ------ | --------------------------- |
| 第一步 | 处理文件（提取文本 / 截图） |
| 第二步 | **OCR**                     |
| 第三步 | 大模型整合成骨架            |

问题出在**把第二步定义成了某个动作**，而不是某类产物。这两者不等价。

举一个当前范围之外的例子来说明为什么：epub、pptx 这类**已经是结构化文字**的输入，走 OCR 是净损失——

|      | 直接提取             | 走 OCR                                                 |
| ---- | -------------------- | ------------------------------------------------------ |
| 文字 | 原始字符串，逐字精确 | "大概率正确"                                           |
| 图片 | 原始嵌入文件         | 截图里裁出来的一块，分辨率被渲染精度锁死，还要再压一次 |

而且是**单向**的，回不去。

所以把第二步按**产物**重新定义：

> **第二步的产物是「块流」，不是「OCR 结果」。OCR 只是块流的一个生产者。**

块流可以来自 DOM、PDF 文本层、或 OCR。这一改，阶段 2 从**固定动作**降成**条件动作**——这就是整个设计里唯一一处为扩展性付出的抽象成本，而它换来的是"以后接新输入不用改后面的阶段"。

## 3. 当前范围与扩展点

### 3.1 当前只做 PDF

输入只有 PDF。**扫描版和数字版走同一条路**：渲染成页面图，再 OCR。

先把一条路走通，不为还没到的输入做特判。

| 阶段       | 职责                              |
| ---------- | --------------------------------- |
| **1 提取** | PDF → 每页一张页面图              |
| **2 识别** | 页面图 → 块流                     |
| **3 归并** | 块流 → 每章一份骨架（注入提示词） |
| **4 打包** | 组装 `.lb`                        |

### 3.2 扩展点

块流这个抽象留了插槽，将来接新输入不必改后面的阶段：

| 扩展                | 插在哪                               | 收益                   |
| ------------------- | ------------------------------------ | ---------------------- |
| epub、pptx          | 阶段 1 换适配器，**阶段 2 整个跳过** | 文字和图片都不再降质   |
| 数字 PDF 改用文本层 | 同上                                 | 拿回精确文字与字号粗体 |
| 其他来源            | 同上，并在 `source` 里声明信任度     | —                      |

后两个扩展要额外处理"阅读顺序"——文本层给精确文字但不给顺序，这正是 OCR 目前顺手解决的问题。**这也是它们被排在后面的原因：收益明确，但不是免费的。**

### 3.3 前三个阶段是机械的，阶段 3 才有意图

前三个阶段只做提取和识别，**不改变内容**。只有阶段 3 注入提示词——它决定产物是原版、是译本、还是重排过的版本（见 6.2）。

## 4. 统一块模型

阶段 2 之后，不管来源，都是同一种块：

| 字段     | 作用                                                      |
| -------- | --------------------------------------------------------- |
| `id`     | 稳定编号，供溯源引用                                      |
| `kind`   | 语义类型：标题 / 段落 / 列表项 / 图 / 书眉 / 页码 / 公式… |
| `text`   | 文字内容                                                  |
| `source` | 来源，决定信任度                                          |

### 4.1 来源决定信任度

| `source`     | 文字可信度                 | 阶段 3 该怎么办          |
| ------------ | -------------------------- | ------------------------ |
| `dom`        | 逐字精确，结构也是读出来的 | 原样搬运                 |
| `text-layer` | 逐字精确，但阅读顺序要推   | 原样搬运，只调顺序       |
| `ocr`        | 可能认错字                 | 可校对，但**修正要留痕** |

当前范围内所有块都是 `ocr`。这个字段仍然保留，因为它是下游判断"这份文字该不该逐字信"的唯一依据——阶段 3 拿到块流时，必须先看 `source` 才知道自己有没有改写权。

### 4.2 块类型是闭集

块的类型必须是我们自己定的闭集，不能把识别服务的标签原样透传。透传等于让服务端的词汇长进下游——阶段 3 的提示词、骨架规范、阅读器都要跟着它变。

所以阶段 2 要有一层映射：服务端标签 → 闭集类型。判定不出来的，**一律兜底成最普通的正文类型**，而不是报错。理由是这样一条兜底让闭集这个前提站得住：新标签进来只会退化，不会让整页解析失败。

**代价**：兜底会静默丢失类型信息，出错时看不出来是哪一类被降级了。这是用"一定成功"换"一定准确"。

### 4.3 块流里不放什么

**不放坐标。** 这一条有两个理由，实现层面的那个才是决定性的。

抽象层面的理由：坐标是页级信息，块流是书级抽象。把页级的东西塞进书级模型，不同来源的块就会长得不一样——"统一块模型"这个前提本身就破了。

但更关键的是，坐标在当前链路上**没有用处**。它原本被指望做两件事，两件都不成立：

- **排序**：实测识别服务返回的块数组顺序**就是**正确的阅读顺序，而按坐标朴素重排会排错（见第 5 节）。
- **裁图**：图由识别服务直接裁好返回，我们不需要自己裁。

两个用途都塌了，坐标就没有留在块流里的理由。**注意这里说的是"不把坐标提升为字段"，不是"信息被销毁"**——服务端裁剪图的文件名里仍然嵌着坐标，只是块流不引用它，也没有任何下游会去读它。

**不放阅读顺序字段。** 数组顺序**就是**阅读顺序。

**但书眉要留着。** 章号常常只出现在书眉里，正文通篇不写"第X章"——它是章节归并的关键线索。书眉不进正文，正文渲染时跳过即可，但不能当噪声删掉。

## 5. 阶段 2 的内部纪律

三条约束，产物里看不到痕迹，但违反了就会产生**无法事后发现**的静默错误。

**1. 不要重排，数组顺序就是阅读顺序；也不要依赖服务端的顺序字段。**
服务端给了一个阅读顺序字段，但它只覆盖部分块类型，其余类型恒为空——所以不存在一个可以完整依赖的顺序来源。而"用坐标自己排一遍"更危险：它在本项目的样本上会排错，坐标在这里是负资产，不是保险。

正确的做法是**原样接受数组顺序**，并把这个判断写进产物：数组顺序即阅读顺序，下游不得再排序。多存一个顺序字段，等于给下游留了一条走错路的机会。

**2. 图片的几何信息不进块流。**
裁图由识别服务完成，返回的就是裁好的成品图，我们只负责下载落盘。因此图片块只需要两样东西：裁剪图的下载地址、以及服务端给的文件名（供下载时建立映射，之后不再使用）。

块流里不出现裁剪框、也不出现图片在页面上的位置。理由与第 4 节一致：这两个用途（排序、裁图）都已经不由我们承担，留着就是没有消费方的字段。

**3. 只用 `JSON.stringify` 写盘。**
文字里会带大量反斜杠（公式、转义序列），而 `\t`、`\n`、`\u` 这些恰好是 JSON 的合法转义——手拼字符串会让它们被**静默改写**。程序化序列化是无损的，所以要禁止模板拼接，写完还要回读校验一遍。

代价是块流一旦生成就不再手工修改。换来的是排版噪声不会渗进数据。

## 6. 阶段 3 的契约

输入：块流 + 变换提示词。输出：每章一份骨架，加一份溯源。

### 6.1 模型直接写骨架

曾考虑让模型只输出"哪些块进哪一节"的编排表、由程序逐字搬运文字。**已否决**。

原因：跨页拼接需要判断。被分页切断的公式、术语、词语，只有模型知道它们该合成一个整体——程序拿到的只是两个残片，无从判断。

模型直接写骨架还有个附带好处：**XML 没有 JSON 那套反斜杠转义陷阱**，只需处理 `<` 和 `&`。第 5 节那类风险到不了这一层。

### 6.2 产物不一定等于原文

用户可能要原版，可能要求译成另一种语言，也可能要求把散落的题目与答案聚合到一起。这些都是**变换**。

设计上的处理：

- 变换由**提示词**驱动，只发生在阶段 3
- 不同版本产出**不同的 `.lb`**，各自完整、各自自足、互不依赖
- `.lb` 必须记录**自己是什么变换的产物**，否则下游无法判断该用哪种校验（见 6.4）

### 6.3 溯源独立成文件，元素不定位

**骨架里不挂任何溯源属性。** 元素不被定位。

溯源是**章节级**的，与章节同名、独立成文件：

```
chapters/0001.xml        纯骨架
chapters/0001.prov.json  这一章用了哪些块、什么变换
```

好处：骨架保持纯净，改骨架规范不用动溯源；溯源的形状不随骨架规范变化；模型也少一个出错点。

**代价必须说清**：没有元素级对应关系，就**无法自动发现"模型编造了内容"**。章节级溯源只能支持下面那条集合校验。

这是有意接受的取舍——粒度换简洁。

### 6.4 校验

**能做的：**

1. 骨架良构
2. 骨架规范合规
3. 资产引用存在
4. **块覆盖校验**：全书各章溯源里块集合的并集，应恰好等于"应该被使用的块集合"，每个块出现且仅出现一次。多一个（编造来源）或少一个（静默丢内容）都会被抓到。这条**对译本同样有效**，因为它比的是集合，不是文字

**做不了的：** 元素级逐字比对（见 6.3）。

**按 `.lb` 自己的变换类型选校验档**——这就是 6.2 里那条"必须记录变换"的用处。

### 6.5 校验发生在写文件时

这是**工具层的行为**，不是阶段 3 自己的逻辑。

模型调用写文件工具、且目标是章节骨架或溯源时，工具在写入后**立即校验，并把诊断作为返回值回给模型**。模型当场改，不用等整章跑完。

**打包时还要终检**：任何一章不合格就拒绝打包。写时校验是给模型的反馈，打包终检是给产物的护栏，两者都要有。

## 7. 稳定层与易变层

流水线效果不好、用户要求改，改的往往不是识别，而是**骨架的组织方式**——例如"图注该独立成块"、"提要要能折叠"、"例题要单独成节"。这类改动只影响阶段 3 的产物。

所以先把数据按**变更频率**分层：

| 层         | 内容         | 变更频率 | 变了之后重跑什么           |
| ---------- | ------------ | -------- | -------------------------- |
| 源层       | 原始文件     | 不变     | —                          |
| 提取层     | 页面图、块流 | 低       | 阶段 1–2（可能花钱）       |
| **骨架层** | **章节骨架** | **高**   | **只重跑阶段 3（不花钱）** |
| 呈现层     | HTML + CSS   | 高       | 阅读器侧                   |

一句话：**把"会变的"和"不会变的"分开，让改版的成本落在最便宜的那一层。**

要让这一点成立，**块流必须随 `.lb` 保留**——它是骨架的原料。留着，改骨架规范就是一次重生，成本与书的大小成正比；不留，就只能写版本之间的迁移器，那会随版本数平方增长。

### 7.1 骨架规范的版本化

1. 每个骨架的根元素自带版本标识
2. manifest 里声明整本用的版本，阅读器不必逐个打开
3. 破坏性变更主版本加一
4. 阅读器声明自己支持哪些版本，遇到不认识的要**明确报错**，不能静默降级
5. 一章一份文件、各自带版本，因此**单章可以独立重跑**
6. 每个版本配一份校验用的 schema 文件

## 8. `.lb` 的结构

本质是 zip，**内部自带原文件的副本**。

```
manifest.json     元信息、骨架版本、章节顺序、资源清单、变换记录
original/         原文件副本
blocks/           块流（稳定层）
chapters/         章节骨架 + 章节溯源（易变层）
schema/           各版本的校验文件
media/            图片资源
```

### 8.1 三条红线

1. **`chapters/` 存的是语义骨架，不是渲染后的 HTML + CSS。** 存了 HTML 就退化成 epub 了。呈现归阅读器
2. **`media/` 里的图是识别服务裁好的成品，原样落盘。** 我们只做下载，不重编码、不缩放、不二次裁剪。图片一旦被我们动过，就等于在"结构化输入提取"这条优势上自己减一档——重编码一次就回不去了
3. **提取阶段不改写内容。** 改写只能发生在阶段 3，而且必须留痕（见 4.1）

## 9. 骨架规范

```
<chapter schema="…" number="04" title="抽象层级">
  <section title="…">
    <p>…</p>
    <figure id="…"><image src="…"/><caption>…</caption></figure>
    <list marker="…"><item>…</item></list>
    <group kind="qa"><question>…</question><answer>…</answer></group>
  </section>
</chapter>
```

元素分三层：

| 层   | 元素                                                                                                |
| ---- | --------------------------------------------------------------------------------------------------- |
| 结构 | `chapter` / `section` / `group`                                                                     |
| 块级 | `p` / `list` + `item` / `figure` + `image` + `caption` + `desc` / `question` / `answer` / `formula` |
| 行内 | `term`（书上印成下划线的术语） / `m`（公式）                                                        |

三条设计约定：

**1. 聚合发生在容器，锚点留在叶子。**
需要把来源不同的内容放到一起时（例如题目和答案原本相隔很远），用**容器**聚合，叶子的文字保持来源单一。叶子合成只用于补断口这种不得已的情况。

**2. 列表标记不是布尔。**
书上会用多种条目符号，还会出现"同一组里标记时有时无"的情况。用一个标记字段表达，而不是"有序 / 无序"两态。

**3. `term` 不是纯文本叶子。**
术语内部会嵌公式、数字、符号；也有取不到内容、需要降级的情况。

## 10. 渲染

| 路线                    | 优点                                     | 缺点                   |
| ----------------------- | ---------------------------------------- | ---------------------- |
| 骨架配样式表直接转 HTML | 声明式、可替换、零依赖；换样式表就换风格 | 逻辑能力弱             |
| 阅读器解析骨架自建 DOM  | 灵活、可交互                             | 风格与逻辑耦合在代码里 |

倾向先用前者打通链路、验证结构（改骨架规范只需改样式表，迭代最快），阅读器成熟后再把渲染逻辑内建。

## 11. 未决事项

1. **引用定位（本版不做）。** 每个块记下它来自原书哪一页，AI 就能引用"第 30 页"、阅读器就能跳过去，痛点里"必须传图"那一条才算解决。难点是**文件内页索引和印刷页码不是一回事**（前言、目录会造成偏移，而且偏移可能不恒定），印刷页码只存在于页脚的数字块里。**另有一条连带代价要记住**：块流不保留坐标，所以将来若要做精确到段落的高亮与划词，只能重跑阶段 2，不能指望从现有产物里补出位置
2. **`ocr` 块的改写权边界。** 目前是"默认原样 + 差异入报告"，但多少差异算"编造内容"、多少算"校正错字"，还没有阈值
3. **阶段 1 的页面图渲染精度。** 服务端裁剪图不由我们决定，但页面图按什么精度渲染、用什么格式存，仍要在体积和识别质量之间定一个点——渲染精度会锁死识别质量，这一步省不得
4. **书眉页码块的去留。** 书眉要留（章号线索），页码目前没有用途
5. **中间产物的目录与命名规范**（页面图、逐页识别结果、块流三者的落盘约定）
6. **`.lb` 是否加密 / 版权标记**
