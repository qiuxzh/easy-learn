# 正文切片（chunking）

把一本书的正文切成一批**带位置的文本片段**：AI 检索原文靠它，阅读器跳到原文也靠它。

本文的目标是**不打开代码也能看懂两件事**——一本电子书是怎么变成这些片段的，以及切完到底长什么样。每一步都标了对应的代码入口，要动手时再往后的「代码结构」和「必须守住的约束」看。

## 这个模块干什么

|        | 内容                                                                 |
| ------ | -------------------------------------------------------------------- |
| 输入   | 一本电子书文件（目前只有 EPUB，HTML / PDF 待接）                     |
| 输出   | `book_chunk` 表里的一批行，每行 = 一段正文 + 这段正文在书里的位置    |
| 谁在用 | AI 检索工具（当检索文档、引用原文）、阅读器（拿位置跳转）、BM25 索引 |

一本 EPUB 进去，出来是几百行：正文平均 600 多字，相邻片段有重叠，每行带一个能跳回原文的位置串。

模块边界：**只管「文字怎么切、切完怎么定位」。不管渲染、不管检索打分、不管分片存放在哪。**

## 过程：一本 EPUB 怎么变成这些行

### 第一步：按阅读顺序拆成「节」

EPUB 内部是一堆 xhtml 文件，`spine` 决定阅读顺序。切片按 spine 顺序逐个文件走，**不跨文件**。取不到正文的节（少数非标准 EPUB 会有）在这里直接跳过，不会留到后面报错。

```
进去：EPUB 文件
出来：一串节，每节带顺序号和节级位置串
      { 顺序 0, 文件 EPUB/ch05.xhtml, 节级位置 epubcfi(/6/22) }
      { 顺序 1, 文件 EPUB/ch06.xhtml, 节级位置 epubcfi(/6/24) }
      ...
```

代码入口：文档源的 `listSegments`。

### 第二步：每节抽出「文本单元」（`loadTextUnits`）

把这一节的 DOM 走一遍，得到一串文本单元。单元是切片的最小单位，**它同时记住内容和一个位置**——「哪个文本节点的第几个字符」。

拿一小节做样本（`<h1>第五章 试错</h1>` + 三段正文，其中一段带 `<strong>` 和 `<br/>`，一段带公式，末尾还有一个 `<script>`）：

```
进去：<h1>第五章 试错</h1>
      <p>在风和日丽的早晨，小王决定<strong>重新开始</strong>。</p>
      <p>他写下两行：<br/>第一行<br/>第二行</p>
      <p>公式 <math display="block"><mfrac><mn>1</mn><mn>2</mn></mfrac></math> 之后继续。</p>
      <script>console.log('ignored')</script>

出来：51 个文本单元，每个是「内容 + 位置」
      "第"              位置 = h1 的第 0 个字符
      "五"              位置 = h1 的第 1 个字符
      ...
      "重"              位置 = strong 的第 0 个字符     ← 进到 <strong> 里，位置跟着换节点
      ...
      "\n"              位置 = 无                       ← <br/> 产生的换行，没有对应位置
      "$$\frac{1}{2}$$" 位置 = mn 的第 0 个字符         ← 整条公式是一个单元，不会被切开
      "\n"              位置 = 无
```

这一步同时决定了**什么不进正文**：

- `<script>`、`<style>`、`<svg>`、`<canvas>`、`<audio>`、`<video>`、`<template>`、`<head>` 整棵子树都不要。这份标签集现在与「按章节读正文」那条路共用；之前两边各有一份、漂移过——正文提取那边漏了 `<head>`，书名会被混进章节开头。
- 图片没有文字就没有内容。
- 公式不丢，而是转成 LaTeX 后**当成一个不可拆分的单元**（优先复用 MathML 里已有的 TeX 注解，没有才自己转换）。
- 块级元素之间补一个换行保住段落边界；同一段文字内部的换行（源码里为了排版加的）会被压成空格。

代码入口：`html-text.ts` 的 DOM 遍历。EPUB 和 HTML 共用这一份，标签集不会分叉。

### 第三步：切成片段（`splitTextUnits`）

切分只看单元的内容，不看位置。规则是四个数字加一条偏好：

```
目标 600 个单元     上下浮动，不强求
硬上限 800          超过就必须断
自然边界下限 300    往前找断点时，低于它就不再往前退
相邻重叠 120        下一片回退 120 个单元，跨段落的答案不至于被切断
偏好：句末          从 600 往后找句末标点，找到才断；找不到就退到 800 硬断
```

40 个段落（1390 个单元）切出来是这样：

```
第 1 片   单元 [0, 620)      头：第1段讲的是同一件事：切分边界要落在句末，重叠用
第 2 片   单元 [500, 1110)   头：句末，重叠用于兜住跨段的答案。\n第16段讲的是同
第 3 片   单元 [990, 1390)   头：句末，重叠用于兜住跨段的答案。\n第30段讲的是同
```

三个现象都能用规则解释：

- 第 1 片是 620 而不是 600：从第 600 个单元往后找句末，到第 620 个才找到，**优先落在自然边界**。
- 第 2 片从 500 开始：`620 - 120 = 500`，重叠是回退出来的。
- **代价**：回退不看句子，所以第 2、3 片都从半句开始（上面「头」就是半句）。这是故意换来的——宁可开头难看，也不要让跨段落的答案被切在边界上。

一节的最后一片是「剩下多少算多少」，所以会出现很短的分片（线上最短的只有 2 个字）。

代码入口：`splitter.ts`。它不认识格式、不认识位置、不认识数据库，输入单元数组、输出切分区间。

### 第四步：头尾位置翻译成位置串（`encodeLocator`）

第二步记住的位置是内存里的对象（某个文本节点 + 偏移），只在这次解析期间有效，必须当场翻译成字符串才能存。

```
进去：起始 = p 节点的第 0 个字符     结束 = p 节点的第 6 个字符
出来：起始 epubcfi(/6/22[ch05]!/2/2/1:0)
      结束 epubcfi(/6/22[ch05]!/2/8/3:6)
```

串的读法：`/6/22` 是第几节（spine 里的位置），`!` 之后是节内的节点路径，`:` 后面是文本节点内的字符偏移。这是 EPUB 标准的 CFI，阅读器用的 foliate-js 能直接拿它跳转和高亮。

节级位置串缺失时不会失败，而是退化成 `epubsec:10`（跳到第 10 节开头）。

代码入口：`locator.ts` 定的约定 + `epub-source.ts` 里的 EPUB 实现。

### 第五步：补上书籍和主键，写进表（`toChunkRows`）

切分产物里没有书籍 id，也没有主键——那是「存到哪」的事。落库时补上：主键 = `书籍 id : 节顺序 : 片内序号`。

## 效果

### 库里长什么样

线上库里的一行真实数据：

```
id            = 1a239990-cec7-4bf7-a152-2dd491b383c3:10:0
book_id       = 1a239990-cec7-4bf7-a152-2dd491b383c3
segment_index = 10
segment_id    = EPUB/ch05.xhtml
chunk_index   = 0
content       = 第五章 试错\n在风和日丽的早晨，小王决定重新开始。…
locator_start = epubcfi(/6/22!/4/2/2/1:0)
locator_end   = epubcfi(/6/22!/4/10/4/9:1)
```

### 必须知道的效果偏差：长度按「单元」算，不是按字符

公式占一个单元，但往往有十几个字符。所以**公式密集的书，分片字符长度会远超 800 的上限**：

```
最长的分片：6100 个字符，里面有 44 个公式
线上 4085 个分片里，303 个达到或超过 800 字符，全部来自公式密集的书
公式密集的那本：26 节切成 682 片，平均每片 1062 个字符
```

这是取舍不是 bug：按字符数切会把公式从中间切开（`$$\frac{1}{2}$$` 变成两半），检索和阅读都会坏掉。所以长度单位是「不可再拆的单元」，公式算一个。**给 AI 估算上下文开销要按字符算，不能按 800 算。**

## 接 HTML / PDF 要动什么

格式差异只有三件事：**怎么遍历、文字从哪来、位置怎么写**。这三件事被隔离在「文档源 + 定位编解码」里，所以切分规则、落库映射、检索链路都不用改。

同一张表里以后会同时存在这几种位置串，这也是列名不能叫 `start_cfi` 的原因：

```
epubcfi(/6/22!/4/2/2/1:0)    EPUB：标准 CFI
epubsec:10                   EPUB：连节级 CFI 都没有时的兜底
html:ch01.html#sec2@12       HTML：元素 id + 文本节点内偏移
pdf:37:4:210                 PDF：页码 : 块序 : 块内偏移
```

| 格式      | 节是什么                 | 文字从哪来             | 位置是什么             |
| --------- | ------------------------ | ---------------------- | ---------------------- |
| EPUB      | spine 里的一个文件       | 文件 DOM               | 文本节点 + 字符偏移    |
| HTML      | 一个文件，或一段标题范围 | 文件 DOM（复用同一套） | 同上，或元素 id + 偏移 |
| PDF / OCR | 一页，或一组块           | 识别结果，不经过 DOM   | 页码 + 块序 + 字符偏移 |

要做的事：写文档源（枚举节、取文字、写位置串）→ 定一个位置串前缀 → 在渲染层加对应前缀的跳转分支 → 只测这个新源的「节、文字、位置串」。

工作量在两处：HTML 是「元素没有 id 时怎么定位」（要退化成子节点下标链，还要考虑文件被编辑后路径漂移）；PDF 是识别结果目前只到页级——识别时没留块序和坐标，所以最多只能跳到页首。

## 必须守住的约束

- **不跨节切分。** 一个分片只能属于一节，这条由类型固化，不是靠约定。
- **位置必须当场翻译成串。** 内存里的位置只在本次解析期间有效，切完再翻就晚了。
- **切分层不许依赖数据库、SQLite、Electron。** 在 `etl/chunking/` 里 grep `db/schema`、`db/repo`、`electron` 应当是零结果。
- **兜底优先于抛错。** 位置串编不出来就退到节级，而不是让整本书一个分片都没有。

## 已知待决

- **节怎么划没有统一答案。** HTML 是整个文件当一节，还是按标题层级切？文件大时前者会切出超长节。PDF 是页还是块，取决于位置能做到多细。
- **两种 DOM 遍历故意没合并。** 切片用的遍历记位置、把软换行压成空格、段落之间只留单换行；章节正文提取用的遍历不记位置、保留软换行、段落之间留空行。同一段 HTML（第一个段落里源码换了行，第二个段落带 `<br/>`）：切片得到 `"第一行 第二行\n第二段\n换行后"`，正文提取得到 `"第一行\n第二行\n\n第二段\n换行后"`。两者共用同一套标签集（标签集漂移过的坑已经收掉），但空白策略不同，合成一个函数必然改掉其中一边的输出。
