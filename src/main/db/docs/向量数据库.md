# 向量数据库

## sqlite-vector使用

向量以 BLOB 存在普通表里，检索走扩展注册的同名虚表 `vector_full_scan`。基于 better-sqlite3 的最小写法：

```ts
import Database from 'better-sqlite3';
import { createRequire } from 'node:module';

// 必须走 CJS 入口：这个包的 ESM 产物里 __require 是「拿不到 require 就抛错」的 shim
const require = createRequire(import.meta.url);
const { getExtensionPath } = require('@sqliteai/sqlite-vector');

const db = new Database('smoke.db');
db.loadExtension(getExtensionPath());

// 1. 普通表 + 普通 BLOB 列，没有「向量表」这种特殊东西
db.exec('CREATE TABLE items (id INTEGER PRIMARY KEY, embedding BLOB NOT NULL)');
const vector = (values: number[]) => Buffer.from(new Float32Array(values).buffer);
db.prepare('INSERT INTO items (embedding) VALUES (?)').run(vector([1, 0, 0, 0]));

// 2. 声明这一列几维、什么类型、什么度量（连接级、不落库，换连接要重声明）
db.prepare('SELECT vector_init(?, ?, ?)').get(
  'items',
  'embedding',
  'type=FLOAT32,dimension=4,distance=COSINE'
);

// 3. 扫描。k 必须绑 BigInt：better-sqlite3 把所有 JS number 绑成 REAL，而它要求 INTEGER
const hits = db
  .prepare(
    `SELECT v.id, s.distance
       FROM vector_full_scan('items', 'embedding', ?, ?) AS s
       JOIN items v ON v.id = s.rowid
      ORDER BY s.distance`
  )
  .all(vector([1, 0, 0, 0]), BigInt(100));
```

`distance=` 支持 `COSINE`（1 − 余弦相似度）、`L2` / `EUCLIDEAN`（同义）、`DOT`（点积的相反数）、`MANHATTAN`，白名单外的值会报错。`vector_quantize(表, 列)` 之后可用 `vector_quantize_scan`，快一到两个数量级、精度损失千分之几，但它**会写库**（影子表 + `_sqliteai_vector` 元数据）。

## 表与访问方式

一共三组表：

- `embed_index`：向量索引注册表。**一套模型参数**一行，记下这批向量存在哪张表、维度多少。
- `embed_task`：一本书的向量化进度。**一本书一行**，记下它的向量属于哪个模型、做到哪了。
- `embed_vec_<维度>_<指纹前16位>`：向量本体，每套模型参数一张。

前两组是**固定表**，结构定义在同级的 `schema/` 目录里，查询走 `getDatabase()`——它返回 drizzle（项目使用的查询构造器）实例，能拿到字段类型推导与 where / join / 聚合。

`embed_vec_*` 的表名按模型生成、不固定，drizzle 的静态 schema 表达不了，读写它只能走 `getRawDatabase()`——它返回底层连接，用来直接执行 SQL。两者共用同一条连接，所以可以在同一个事务里混用。

## 模型身份与指纹

库里可能同时存在好几批向量：用 A 服务算的、用 B 服务算的。一批向量属于哪个向量空间，
取决于它出自哪一套模型参数：**请求地址 + 模型标识 + 向量空间版本**。

这三样拼起来算一次 SHA256，得到一串 64 位十六进制字符，作为这套参数的**指纹**：

```
sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
```

指纹是 `embed_index` 唯一的查找键。**它的计算规则不在本模块**，见 `shared/utils/embedding-identity.ts`；
本文只关心它在存储里的两个用途：注册表的唯一键，以及向量表名的后缀。

指纹里**不含维度**，所以第一次调用接口之前就能拿它查库——维度是查到记录之后才知道的，
放在 `embed_index.dimension` 里。维度的权威来源是首次成功调用接口后响应向量的长度；
配置里的 `dimension` 只是设置页探测出来的快照，可能为空、也可能过时，一律不作依据。

## 动态表名

`embed_vec_*` 在运行时创建，表名由三段拼成：

```
embed_vec_1024_9f86d081884c7d65
          │    └── 指纹前 16 位（64 bit）
          └─────── 向量维度
```

**为什么一套参数一张表。** 见开头的约束：一列只能承载一个维度。不同模型的维度不同（768 / 1024 / 1536），塞进同一列里扫描会算出错误的距离，而且不报错。
所以维度隔离必须落到物理表上，不能靠「单表加一列模型标识再过滤」实现。

**后缀为什么取指纹而不是自增 id。** 两个理由：一是维度一确定就能算出表名，于是「建表 → 注册索引 → 写向量」可以在同一个事务里按自然顺序完成，不会出现孤儿表；二是幂等，同一套模型参数重复注册永远得到同一个表名。
