# 向量数据库

**本文只讲存储**：表结构、字段语义、数据不变式。

向量化任务怎么跑（批次怎么切、什么时候重试、运行态放在哪）属于编排层；
一本书在界面上显示成什么状态属于展示层。两者都不在这里。

## 依赖的检索扩展

向量检索由 **sqlite-vector** 提供：一个 SQLite 的加载式扩展，向量直接以 BLOB 存在普通表里，
不需要虚表。它**按「表 + 列」声明维度**，声明入口是扩展提供的 `vector_init`。

这条声明带来一个必须记住的性质：**一列只能有一个维度，而且扫描时不校验**。
维度混进同一列不会报错，只会算出错误的距离。

本模块的表结构就是被这一条推出来的，下面几节都围绕它展开。

## 表与访问方式

一共三组表：

- `embed_index`：向量索引注册表。**一套模型参数**一行，记下这批向量存在哪张表、维度多少。
- `embed_task`：一本书的向量化进度。**一本书一行**，记下它的向量属于哪个模型、做到哪了。
- `embed_vec_<维度>_<指纹前16位>`：向量本体，每套模型参数一张。

前两组是**固定表**，结构定义在同级的 `schema/` 目录里，查询走 `getDatabase()`——它返回 drizzle（项目使用的查询构造器）实例，能拿到字段类型推导与 where / join / 聚合。

`embed_vec_*` 的表名按模型生成、不固定，drizzle 的静态 schema 表达不了，读写它只能走 `getRawDatabase()`——它返回底层连接，用来直接执行 SQL。两者共用同一条连接，所以可以在同一个事务里混用。

## 模型身份与指纹

库里可能同时存在好几批向量：用 A 服务算的、用 B 服务算的。一批向量属于哪个向量空间，
取决于它出自哪一套模型参数：**请求地址 + 模型标识 + 向量空间版本**。

这三样拼起来算一次 SHA256，得到一串 64 位十六进制字符，作为这套参数的**指纹**：

```
sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
```

指纹是 `embed_index` 唯一的查找键。**它的计算规则不在本模块**，见 `shared/utils/embedding-identity.ts`；
本文只关心它在存储里的两个用途：注册表的唯一键，以及向量表名的后缀。

指纹里**不含维度**，所以第一次调用接口之前就能拿它查库——维度是查到记录之后才知道的，
放在 `embed_index.dimension` 里。维度的权威来源是首次成功调用接口后响应向量的长度；
配置里的 `dimension` 只是设置页探测出来的快照，可能为空、也可能过时，一律不作依据。

## 动态表名

`embed_vec_*` 在运行时创建，表名由三段拼成：

```
embed_vec_1024_9f86d081884c7d65
          │    └── 指纹前 16 位（64 bit）
          └─────── 向量维度
```

**为什么一套参数一张表。** 见开头的约束：一列只能承载一个维度。不同模型的维度不同（768 / 1024 / 1536），塞进同一列里扫描会算出错误的距离，而且不报错。
所以维度隔离必须落到物理表上，不能靠「单表加一列模型标识再过滤」实现。

**后缀为什么取指纹而不是自增 id。** 两个理由：一是维度一确定就能算出表名，于是「建表 → 注册索引 → 写向量」可以在同一个事务里按自然顺序完成，不会出现孤儿表；二是幂等，同一套模型参数重复注册永远得到同一个表名。

## 字段语义

`embed_index`：

- `fingerprint`：唯一键，见上一节
- `table_name`：这批向量落在哪张表。它由维度与指纹拼出，不依赖自增 id，所以插入时就能填上
- `model_id`：请求时传给接口的 model 名，仅供展示与排查
- `dimension`：向量维度，喂给 `vector_init` 的唯一权威来源
- `last_label` / `created_at` / `last_used_at`：配置里的键名与两个时间戳，供排查

`embed_task`：

- **主键是 `book_id`：一本书只有一行。** 它换来的是状态的互斥性——一份数据要么属于当前模型、
  要么属于旧模型，不可能同时是「已向量化」和「未向量化」
- `embed_index_id`：这份数据属于哪个模型，对应 `embed_index.id`
- `total`：分片总数。它是 `book_chunk` 计数的副本，**重新分片时必须删掉这些行**，否则会过期
- `done`：已有向量的分片数。与写向量同事务累加，所以不会滞后于向量行
- `last_error`：最近一次停下的原因，任务开始时清空
- `updated_at`：最近一次写入时间

**没有「跳过」也没有「失败明细」。** 某个单元该不该处理属于调用方的策略，本模块只知道它做成了
还是没做成；做失败的那一批本来就没有向量行，下次重来时自然会被重新取出。

## 数据不变式

**`done` 必须与向量行同事务写。** 这是全项目唯一一处「两处记同一件事」，靠原子性保证
`done` 不滞后。拆开写的话，统计会比真实的多，而且不会报错。

**删除只删本资源。** 删书、重新分片是「删这本书在**所有**向量表里的行 + 删它的进度行」，
不是清空整表。这些跨表操作收在 `db/repo/book-embedding-repo.ts`：调用方各写一遍的话，
漏一处就会留下孤儿向量——那些行再也找不到，只会白占空间。

**进度行可以按向量表重建。** 写入是同事务的，正常运行时不会产生缺口；但换 schema、
或者手工改过库之后可能对不上。`bookEmbeddingRepo.reconcile()` 在启动时按书对账一次：
有向量却没有进度行的补上，幂等，跑多少次都一样。表结构变更时也是直接丢掉旧表靠它重建
（见 `db/index.ts` 的 `dropLegacyEmbedTask`）。
